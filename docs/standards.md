# STKCraft standards

The rule book. `AGENTS.md` says how to work in this repository; this document says what the product
must be, in the areas where a decision made once is expensive to unmake. Every rule here is either
enforced by a task in `cargo xtask ci` or marked as unbuilt, and a rule that is neither is a wish.

STKCraft is one of the ArtCraft Craft apps. Where the family has a standard, this project follows it
rather than inventing a local variant, and the section says which family repository owns the
standard. The family's own documents are the authority; this one records what conformance means
here.

| Area | Standard | Enforced by | State |
|---|---|---|---|
| Interface translations | `storytold/craft-i18n` catalog format | `cargo xtask i18n` | built |
| Agent + skills + MCP | `storytold/craft-ai-integrations`, `craft-skills` | `cargo xtask ci`, `cargo xtask layers` | built, see §2 |
| The user's own documents | this document, §2a | `cargo test` (ranking, citations, misses) | built |
| Licensing | MIT OR Apache-2.0, the family's | the two licence files | built |
| Extensions and plug-ins | `storytold/craft-extensions` package contract | `cargo test` (feature and trust tests) | partial, see §3 |
| API documentation | this document, §4 | `cargo xtask api-docs check` | built, see §4 |
| UI library and fonts | `storytold/craft-libs` (`craft-ui`), `storytold/egui` fork | `cargo test`, `[patch.crates-io]` | built |

## 1. Language and translation

**One English source; every other language is a catalog.**

- The interface is written in English in the source, and every user-visible string goes through
  `tr!`, `trc!` or `trn!`. A string built at run time cannot be extracted and cannot be checked, so
  the macros take literals only. `cargo xtask i18n` extracts them; `cargo xtask ci` runs it.
- Catalogs are the family format: `locales/<locale>/stkcraft.tsv`, three TAB-separated columns
  `context <TAB> English <TAB> translation`, English as the key, `@plural` / `@id` / `@msg` contexts,
  `{name}` placeholders and a trailing `…` preserved in both columns, `@id	language.name` naming the
  language. `docs/guides/localization.md` is the long form.
- **English is always complete by construction** — it is the source. A translation is always partial
  by default and may be so forever: a missing row shows English, never a blank or a key.
  `locales/zh/stkcraft.tsv` is the first shipped catalog, generated by the pipeline and reviewed row
  by row before it landed.
- **Machine translation is how a catalog gets made, and review is how it ships.** `cargo xtask i18n
  translate` fills a locale from the user's own `DEEPSEEK_API_KEY`; the rows it produces are
  proposals, and a wrong translation is worse than a missing one because the missing one shows
  English and the wrong one is believed. A release ships only catalogs someone has read.
- **The translation path stays outside the window's startup path.** A build with no `locales/`
  directory is a valid English-only build; a window that is merely open never makes a network call.
  A person who wants a language the build does not carry asks for it in the panel, and that request —
  their key, their machine, their language — is the only way the window translates itself. The result
  is written to their configuration directory, never into the checkout.
- **Not translated:** command ids, scenario and satellite names, machine-formatted times, and
  computed values. The family's rule is interface chrome, not document text.
- **Not built:** number and date localization per region, and right-to-left layout.

## 2. Agent, skills and the Model Context Protocol

**The model is outside the kernel, and the kernel is completely reachable from outside it.**

- `stkcraft-engine` and everything below it makes no network call, links no HTTP client and does not
  know a language model exists. `stkcraft-mcp` (L5) is a transport onto the command registry;
  `stkcraft-agent` (L6) is a client of that transport. The agent therefore cannot reach a capability
  the protocol does not expose, which keeps "an agent can do anything a user can" a property of the
  design rather than a promise.
- **Every command is a tool**, generated from the registry: one descriptor with a label, a menu path,
  documented parameters and a declared `ParameterKind`. A capability is added by adding a command,
  never by teaching a model a number.
- **A tool returns the answer, not a count.** Computed times come back as text a model reads and as
  `structuredContent` a program can trust.
- **Skills are documents, not code**: `share/skills/<name>/SKILL.md`, one `#` heading whose text is the
  description, then the procedure, what the answer means and the traps. They are listed in the system
  prompt by name and read only when a job needs one — the same progressive disclosure an MCP client
  gets from `prompts/get`. The family's shared skill corpus is `storytold/craft-skills`.
- **The provider is a connection, not a hard-coding.** `DeepSeek` is the default because it is what
  this project can test, and `ChatModel` is a trait so a different model is a different
  implementation. A key comes from the environment and is never written to a document. Where the
  family layer (`craft-ai-integrations`: connections, model binding, consent, jobs) provides the same
  thing, adopting it replaces this code rather than living beside it.
- **Consent is the user's action.** A question typed into the assistant panel or `stkcraft chat` is a
  request to use a model; nothing else in the app calls one.

## 2a. The user's documents come before the model's memory

**A number is either traced to a source or it is not an answer.** The platform reads the person's own
documents — their requirements, data sheets, notes — before a model says anything, and the ordering is
the product.

- **Every factual or numeric question starts with a search of the library.** The agent's prompt makes
  it rule one, and the tool is named in the same prompt. A model that answers first and cites
  afterwards has already produced the answer nobody can check.
- **A hit is a citation, not a summary**: document path and line range, so a person opens the file and
  reads the sentence the model used. `stkcraft knowledge "<query>"` prints the same citations the
  model sees.
- **"Nothing matched" is an answer.** The search reports `missed`, the tool says so in words, and the
  prompt requires the model to say the library does not cover the question before it offers general
  knowledge — labelled as general knowledge. A retrieval that always returns something is a retrieval
  that always lies about its evidence.
- **Ranking is deterministic.** Lexical (BM25) with no embedding model, because the numbers this
  project cares about are exact tokens and because a test can only assert an order that is the same on
  every machine.
- **Hostile input is bounded before it is read**: file count, file size, depth, no symlinks below the
  root, UTF-8 only. Pointing the library at `/` is slow, not fatal.
- **The documents win ties.** Where a document disagrees with the model's general knowledge, the
  answer follows the document and says which one.
- **Not built:** PDF/DOCX/XLSX text extraction (extract beside them), page-level citations, an index
  cache, and the side-by-side comparison of a document's answer with the engine's computation.
  `docs/design/knowledge.md` states each limit.

## 3. Extensions and plug-ins

**Third-party code is designed in and switched off.** The family's `craft-extensions` contract is
the model: a package manifest, trust tiers assigned by the host rather than claimed by the package,
a shared on-disk store, themes carrying no code, and plug-ins whose v1 permission list must be empty.

- **What a plug-in is today is a registration**, not a loaded shared object: a command (one registry
  entry), a skill (one markdown document), or a bulk file (one verified row in `cargo xtask
  fetch-data`). Anything expressible that way is a plug-in now.
- **The package contract is implemented** in `stkcraft-extensions`: a manifest that never states its
  own trust level, ids checked by character class so they are safe as directory names, theme
  packages that may carry no code, permission lists that must be empty, and a `third-party` feature
  that no release build enables — with a test that fails if it ever becomes a default.
  `stkcraft extensions` lists what is installed and why a package was refused.
- **Dynamic code needs a capability story first** — what a plug-in may read, compute and spend — and
  a story invented after the fact is a hole. Until that story exists and passes review, this project
  runs no third-party code.
- **Not built:** the store (bounded unpacking, atomic installs, enable-per-app), the index, the
  signature check and any code execution at all. A package on disk is data; nothing loads it, and a
  plug-in package is refused by name until a capability model exists. Unpacking, when it lands, must
  be bounded in count, size and ratio with no path leaving its folder.

## 4. Documentation and API documentation

**Documentation is written in English and generated where it can be.**

- Prose documents live in `docs/`, one subject each, and are English. A document that describes the
  code is a claim about the code and is updated in the same commit that changes it.
- **The API reference is generated from the code**, not written by hand: `cargo xtask api-docs`
  reads the workspace's doc comments and the command registry and writes a Markdown reference. A
  hand-written list of commands is a list that drifts; the generated one cannot.
- **The generated reference is translated, not re-authored.** Only the English source is maintained;
  `cargo xtask api-docs --translate --language <code>` (or the same DeepSeek key, the same pipeline)
  produces `docs/api/<code>/…` from it. A translated page is a build artifact and says which English
  revision it came from, so a stale translation is visible rather than trusted.
- **A number in documentation that the code computes is marked as an example**, because prose does
  not re-run when the code changes.
- **The gate checks, it does not write.** `cargo xtask ci` fails when `docs/api/en/index.md` is
  stale; `cargo xtask api-docs` rewrites it. A gate that rewrites the file it checks passes on its
  first run and hides a stale reference for ever after.
- **A translated reference names its English revision**, so a page that lags behind the code says so
  rather than being trusted. The translation memory (`docs/api/<locale>/strings.tsv`) is what makes a
  second run cheap and a review possible.
- **Not built:** the reference covers the command surface, the crates and their module documentation.
  It does not yet document every public item's signature, and command parameter *descriptions* stay
  English in the reference — they are translated in the interface, where the catalogs carry them.

## 5. The interface library

**The window is drawn with the family's stack, not with a local arrangement of `egui`.**

- **The egui version is the family's fork**, pinned by revision in `[patch.crates-io]` — the same
  `storytold/egui` commit every Craft app builds against, with `storytold/winit` beside it. A widget
  behaves the same in all of them, and a fix lands once instead of once per app. The revision is a
  review, never a caret range; bumping it is its own change.
- **The UI library is `craft-ui`** from `storytold/craft-libs`, at the one revision every
  `craft-*` dependency uses. An app that invented its own theme tokens, font stack or combo box
  would drift from eight siblings at once.
- **Text is drawn by the family font stack** (`craft_ui::fonts::UiFonts`): the app's faces, then the
  shipped faces for the interface language and the other scripts, then **the fonts installed on the
  machine**, then emoji and `egui`'s defaults. `egui` alone ships a Latin face, so a Chinese,
  Japanese, Korean, Arabic or Thai label is tofu boxes without this — which is precisely what this
  project shipped until 0.1.30.
- **A shipped catalog's characters are covered by a test**: `craft_ui::fonts::missing_glyphs` over
  every embedded catalog, so "the Chinese looks wrong" becomes a named character and a named string.
  `STKCRAFT_FONTS=off` turns the installed fonts off, which is the reproducible-tofu switch: text
  that draws the same on every machine, and the fastest way to prove a glyph problem is or is not
  the machine's fonts.
- **No font file is committed.** Fonts come from the machine, or from
  [`storytold/craft-fonts`](https://github.com/storytold/craft-fonts) as an optional build input —
  the family rule every Craft app follows.

## 6. Family interop and licensing

**To be one of the Craft apps is to be interchangeable with them**, so the interchange points are
fixed from the start rather than retrofitted.

- **Licence: `MIT OR Apache-2.0`**, the family's choice, with **both licence texts in the repository**
  (`LICENSE-MIT`, `LICENSE-APACHE`) and `NOTICE` naming them. The MIT text is the standard one, the
  copyright holder is the ArtCraft Team and the contributors, and a dependency whose licence is not
  compatible with that pair does not enter the build. Brand assets are not covered by it — the ArtCraft
  name and marks belong to the family.
- **Translations interchange with `storytold/craft-i18n`**: the catalog format is theirs (§1), so a
  translation written here can be contributed there and a catalog from there works here.
- **Extensions interchange with `storytold/craft-extensions`**: the package contract is theirs (§3),
  so a theme or skill pack aimed at the suite can be aimed at this app.
- **The AI layer is the family's direction**: the connection/model/consent shape of
  `storytold/craft-ai-integrations` is what this project's agent should adopt when those crates are
  stable; today the transport is local (`curl`), the contract is the same one (tools, resources,
  prompts, no model in the kernel), and the gap is stated rather than hidden.
- **The UI is the family's stack** (§5): the pinned `storytold/egui` fork, `craft-ui`, the shared font
  stack.
- **Fonts, bulk data and corpora stay outside the repository**: `craft-fonts`, the NASA kernels via
  `cargo xtask fetch-data`, and the user's own documents in their configuration directory.
- **Not built: the control channel.** The siblings expose `--control <port>` with a token file so a
  launcher or another app can drive them; STKCraft has a CLI and an MCP server but no control socket
  yet, so a launcher cannot drive it the way it drives GridCraft. That is the first interop item on
  the list, and it is named here so it cannot be forgotten.

## 7. Crate taxonomy

**A crate's place in the tree says what it is.** A reader — especially a professional one — should be
able to tell the platform from the domain from the presentation without opening a file, so the tree is
grouped by subject and every group has a rule about what may live in it.

| Directory | What belongs there | Rule |
|---|---|---|
| `crates/framework/` | the platform: units, time, translations, persistence, the extension contract | nothing here may know what an orbit is. A name like `body` or `access` appearing here is a bug |
| `crates/astro/` | the orbital-analysis domain: bodies, frames, ephemerides, propagation, access geometry, the engine | the astronomy lives here and nowhere else. Every constant and formula carries its source |
| `crates/agent/` | the model-facing surface: the knowledge base, the MCP server, the agent runtime | a crate here drives the engine through the command registry and may not reach past it |
| `crates/ui/` | presentation | may use GPU and windowing crates; may not compute physics |
| `apps/` | the deliverable: window, CLI, MCP server and assistant wiring | thin: every behaviour it offers is a command or a transport |
| `xtask/` | the build tool | sits outside the layer graph |

- **A new crate goes into the directory that matches its subject**, and `cargo xtask layers` fails for a
  workspace member that is not in the table, so the taxonomy cannot quietly grow a fourth category.
- **Names keep the `stkcraft-` prefix** rather than a domain prefix: `stkcraft-body` is unambiguous
  inside `crates/astro/`, and the family's convention is one prefix for the app's crates.
- **The layer number and the directory agree**: framework ≤ 4, astro 2–4, agent 3–6, ui 5, apps 6. A
  crate that needs a higher layer than its directory implies is in the wrong directory.

## 8. Storage

**Do not scatter state.** Every stored thing belongs to one of three stores, chosen by the question a
reader asks of it, and `docs/design/storage.md` is the decision record:

- **relational** for the record — scenarios, their revisions, the contents, the computed windows, the
  provenance of each run, documents and citations, translation rows, installed packages;
- **key-value** for derived, disposable caches — kernel indexes, the knowledge inverted index, vectors,
  generated catalogs;
- **vector** for recall over a large corpus, once an embedding model is chosen — candidates only, never
  the authority.

- **One crate owns persistence.** No other crate opens a database, writes a key-value file or issues
  SQL; a crate that needs to remember something asks the storage crate.
- **Config is what a person decided, data is what the program produced.** They live in different
  directories, and deleting the cache never loses a decision.
- **Every stored value that came from outside carries its digest**, so a record can be reproduced.
- **Not built:** the storage crate itself, the PostgreSQL path, embeddings, and the corpus fetcher.
  `docs/design/storage.md` §6 states each.

## 9. Repository layout

**The root is a map, not a pile.** Every top-level entry has one job, a reader can tell the job from
the name, and a thing that does not fit an entry is in the wrong place. This is the layout; §7 is the
same idea one level down, inside `crates/`.

| Entry | What lives there | What may not |
|---|---|---|
| `crates/framework/` | the platform: units, time, translations, extensions, (next) storage | anything that knows what an orbit is |
| `crates/astro/` | the orbital-analysis domain: bodies, frames, ephemerides, propagation, access, engine | network access, model calls, GPU |
| `crates/agent/` | the model-facing surface: knowledge, MCP, runtime | reaching past the command registry into the engine's internals |
| `crates/ui/` | presentation: the viewport | computing physics |
| `apps/stkcraft/` | the deliverable: window, CLI, MCP server, assistant wiring | behaviour that is not a command or a transport |
| `xtask/` | the build tool and every policy check | being depended on by anything above `TOOL_LAYER` |
| `share/` | **content the app loads**: `share/locales/<locale>/stkcraft.tsv`, `share/skills/<name>/SKILL.md` | code, or licensed artwork (that is `docs/images/` + `ATTRIBUTION.md`) |
| `docs/` | the engineering record, indexed by `docs/README.md`: `standards.md`, `design/`, `guides/`, `api/`, `plans/` | generated text outside `docs/api/` |
| `packaging/` | installers and their shared values (`env.sh`) | application code |
| `contributors/` | `people.toml`; `contributors.json` is generated | hand-edited credits |
| `data/` | **fetched bulk data, gitignored**: kernels, Earth orientation, catalogues | anything committed |
| `plan/` | local working notes, gitignored | anything a reader needs |
| root files | `README.md` (what this is), `CHANGELOG.md` (the release record), `CONTRIBUTING.md`, `AGENTS.md` (how to work here), `NOTICE`, `ATTRIBUTION.md`, the two licence texts, `Cargo.toml`/`Cargo.lock`/`rust-toolchain.toml` | a second place for any of them |

Three rules keep the map honest:

- **Content is not scattered beside the source.** What the app loads at run time lives under `share/`,
  named by kind, and a deployment copies `share/` beside the binary. A skill document or a catalog
  dropped in the repository root is the failure this table exists to prevent.
- **Generated and fetched things are never committed.** `docs/api/` is generated but *is* committed,
  because the gate checks it; `data/` is fetched and is not; `contributors.json` is generated at
  release time. The difference is whether a reader can reproduce it from the repository alone.
- **Documents have a home by kind, not by date.** A decision goes in `design/`, a how-to in `guides/`,
  a rule in `standards.md`, a plan in `plans/`. `docs/README.md` is the index, and it is what a
  newcomer reads after the README.

## 10. What every rule here has in common

- **The gate is the enforcement.** A rule that `cargo xtask ci` does not check is a rule that will be
  broken by the next contributor in good faith. When adding a rule, add the check.
- **Unbuilt work is stated as unbuilt.** `CHANGELOG.md` has a "Not built yet" section for every
  version, and this document marks the rules that describe something not yet shipped. A reader must
  never have to guess whether a paragraph is a promise or a description.
- **The family wins ties.** Where this document and a family standard disagree, the family standard is
  right and this document is the bug.
