# Engine implementation plan

> Steps use `- [ ]` checkboxes. Each task ends with `cargo xtask ci --offline` passing and a
> commit that states Why / What changed / Verification / Known gaps.

**Goal:** Join the four numerical layers into something that runs: a scenario document holding
satellites, stations and sensors; a command table that is the single entry point for every user
action; and the wiring that turns a two-line element set into access windows.

**Architecture:** A new crate `stkcraft-astro-engine` at L4, above `stkcraft-astro-access`. It owns three
things and nothing else: the **scenario** (typed, validated, serialisable), the **command
table** (ids, labels, parameters, `enabled`, `run`), and the **analysis** that walks a scenario
over a timeline. The command table is the contract every transport binds to later — menus,
shortcuts, CLI, control channel — so it is built and tested before any UI exists.

**Tech stack:** Rust 2024, `stkcraft-{core,time,frames,sgp4,access}`, `serde`, `serde_json`.

## Global constraints

- No panics in non-test code; the standard deny block plus `#![forbid(unsafe_code)]`.
- Test modules use `#[expect(clippy::expect_used)]`, adding `clippy::panic` only when the
  module actually panics.
- Every formula or constant cites its source. This arc mostly composes sources already cited
  in the layers below; where it introduces one (the default step, the Earth model choice) it
  says why.
- Programmatic calls use defaults and never open a dialog — there is no dialog to open yet, but
  the command signatures are shaped so that stays true.
- Register the crate in `xtask/src/layers.rs` (L4) and `PORTABLE_CRATES`.
- `cargo xtask ci --offline` before every commit. **Never run `cargo` without `--offline`.**

## Design decisions up front

**A scenario is data, not behaviour.** Satellites carry their element set and a colour; stations
carry their geodetic position and sensor. Nothing in the document knows how to propagate. That
keeps serialisation honest and means a saved scenario cannot change meaning when the physics
improves — it will produce different numbers, and that is the correct outcome, but the document
itself is unchanged.

**Every user-visible action is a command.** The tests exercise the table directly, which is the
same path a menu click or an MCP call will take. That is what makes "an agent can do anything a
user can" checkable rather than aspirational.

**The engine holds no global state.** `run` takes `&mut Scenario` and returns a typed result.
A control channel will wrap that in a mutex; nothing in this crate assumes it.

**Propagation is memoised per (satellite, time).** The window finder evaluates the target
position several times per boundary, and a second evaluation at the same instant must return
the same answer or the bisection is not searching a function.

### Task 2: Propagating a satellite to an Earth-fixed position

**Files:** `crates/engine/src/propagate.rs`

This is the join that had no home: TLE → SGP4 → TEME → GCRF/ITRF.

**Interfaces:**

```rust
/// A satellite prepared to propagate, with its frame context.
pub struct Propagator { satellite: Satellite /* internal sgp4 */, ... }

impl Propagator {
    pub fn new(tle: &TwoLineElement) -> Result<Self>;
    /// Earth-fixed position at an offset from the element set's epoch.
    pub fn itrf(&mut self, at: Offset) -> Result<[f64; 3]>;
    /// GCRF position, for the viewport later.
    pub fn gcrf(&mut self, at: Offset) -> Result<[f64; 3]>;
}
```

**The subtlety that must be documented:** SGP4 is stateful — the resonance integrator carries
`atime`, `xli`, `xni` across calls — so a `Propagator` cannot be shared between threads and
cannot be asked for times out of order without the integrator restarting. The window finder
asks for times in ascending order within a bracket and then back-tracks, which resets the
integrator; that is *correct* (the reference defines the restart) but the cost must be
acknowledged.

### Task 4: The command table

**Files:** `crates/engine/src/commands.rs`

```rust
pub struct CommandDescriptor {
    pub id: &'static str,
    pub label: &'static str,
    pub menu_path: &'static str,
    pub shortcut: Option<&'static str>,
    pub parameters: &'static [Parameter],

pub struct Parameter {
    pub name: &'static str,
```

## Self-review

**Spec coverage.** The sibling apps' rule is "everything is a command" and "an agent can do
anything a user can". Task 4 is the whole of that, tested through the registry rather than
through a UI. The layering rule is respected by placing the engine at L4.

**Placeholder scan.** No step says "later". Task 2's out-of-order test states the SGP4
statefulness issue explicitly rather than leaving it to be discovered.

**Type consistency.** `SatelliteId`/`StationId` newtypes are introduced in Task 1 and used in
Tasks 3 and 4. `Offset` in Task 2 is `stkcraft_time::Epoch`-relative seconds; it is aliased
rather than replaced so the public surface uses the time crate's type.
