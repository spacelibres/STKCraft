# 3D viewport implementation plan

**Goal:** `cargo run -p stkcraft` opens a window showing the Earth and the satellites in a
scenario, rotating freely, so the analysis that already works can be seen.

**Architecture:** A new crate `stkcraft-ui-viewport` at the UI layer, below the app and above
nothing — it may use egui, per `LAST_NON_UI_LAYER`. It owns a `wgpu` render pass and an egui
overlay; the app crate owns the window (`eframe`) and feeds the viewport a **frame** of
already-computed positions. The viewport never propagates: it draws what the engine hands it,
so replacing it cannot change an answer.

**Tech stack:** `eframe` (window + egui), `wgpu` (via `eframe`'s re-export so versions cannot
drift), `bytemuck` for vertex upload. No math crate: the engine already produces positions, and
the four view matrices are written by hand in thirty lines rather than pulling in `glam`.

## Global constraints

- No panics: the standard deny block. A GPU failure returns `Error::Unsupported` or is reported
  in the UI, never panics. `wgpu` cannot be entirely `?`-chained, so every `Option` is handled.
- The viewport crate is **above** `LAST_NON_UI_LAYER`, so it may use egui; nothing below may.
- Register in `xtask/src/layers.rs` at `APP_LAYER - 1`, and **do not** add it to
  `PORTABLE_CRATES` — it cannot build for wasm without a canvas host, which is a later arc.
- `cargo xtask ci --offline` before every commit. Adding egui/wgpu means the lock file grows;
  that is expected and the vendored crates are fetched once.
- Assets: the Earth and the star field are **drawn in code** — a UV sphere and a procedural star
  field — so nothing needs an `ATTRIBUTION.md` row. This is the stated preference in `AGENTS.md`.

## Design decisions

**Orbits are drawn as line strips from propagated positions,** not as Keplerian ellipses. An
osculating ellipse from the current elements is wrong the moment drag or J2 matters, and the
viewport must not show something the engine did not compute.

**The camera is a turntable** around the Earth centre: azimuth, elevation, distance. Mouse drag
rotates, wheel zooms. That is the whole navigation model; a fly camera is a later feature.

**The Earth is untextured.** A procedurally shaded sphere with a latitude/longitude graticule
reads clearly as a globe, carries no licence, and is honest about what the app knows. Coastlines
would need a data file with a source and a checksum, which is a separate decision.

### Task 1: The crate, the frame type, and the camera

**Files:** `crates/viewport/src/{lib.rs,camera.rs}`

```rust
pub struct Camera { pub azimuth: f32, pub elevation: f32, pub distance_km: f32 }

/// Everything the viewport needs to draw one instant. Computed by the engine.
pub struct Frame {
    pub epoch_label: String,
    pub earth_radius_km: f32,
    pub satellites: Vec<SatelliteGlyph>,
    pub tracks: Vec<Vec<[f32; 3]>>,   // GCRF km, one polyline per satellite
}

pub struct SatelliteGlyph { pub position_km: [f32; 3], pub color: [u8; 3] }
```

Tests: the camera's view matrix maps the origin to a point at `distance`; rotating the azimuth
by π lets us see the far side (the z sign of a point flips); the projection maps the frustum
edges correctly at a known field of view.

---

### Task 2: The geometry generators

**Files:** `crates/viewport/src/geometry.rs`

- `sphere(radius, stacks, slices) -> (Vec<Vertex>, Vec<u16>)` — a UV sphere.
- `graticule(radius, step_deg) -> Vec<[f32;3]>` — latitude and longitude lines as line-list vertices.
- `star_field(count, seed) -> Vec<[f32;3]>` — deterministic pseudo-random directions.

Tests: the sphere's vertices all lie on the radius; the triangle count is `stacks × slices × 2`;
the graticule has the expected number of segments; the star field is deterministic for a seed
and every direction is unit length.

---

### Task 3: The wgpu renderer

**Files:** `crates/viewport/src/renderer.rs`

One pipeline for triangles (the Earth), one for lines (orbits, graticule, stars). Depth test on.
No textures. The shader is a WGSL string in the source: a diffuse-ish shaded sphere for the
Earth and flat colour for lines.

Tests: the vertex-buffer layout matches the struct (checked by construction); the pipeline
descriptors are validated by the type system, so what is testable here is the shader's
compilation, which is only possible with a GPU. That limitation is stated in the commit rather
than hidden.

---

### Task 4: The eframe application

**Files:** `apps/stkcraft/src/app.rs`, `main.rs` gets a subcommand switch

- No arguments → open the window.
- `passes …` → the CLI table that already works.

The app holds a `Scenario`, a `Propagator` per satellite, and recomputes the `Frame` when the
clock advances. A side panel shows the scenario summary and the access windows.

Tests: the frame builder (in the engine, not the app) at a known epoch produces the published
positions; the app's clock advance is deterministic given a fixed step.

---

### Task 5: Release 0.1.0

The first release where the version's minor digit changes: the product now has a UI.

## Self-review

**Spec coverage.** `AGENTS.md` requires the UI to be thin and the viewport swappable — Task 1's
`Frame` is the whole interface, and the viewport has no dependency on the engine or the access
layer. The "never break wasm" rule is respected by keeping the viewport out of `PORTABLE_CRATES`.

**Risk.** `wgpu` in a sandboxed environment may fail to initialise (no display, no adapter). The
commit must state whether the window was actually opened, and if not, exactly why — not claim a
screenshot exists when it does not.

---

## Outcome

Shipped in 0.1.0. The plan held up in structure and was wrong in four places, all recorded
here because the next arc will make the same assumptions:

1. **`eframe` 0.37 does not have the API the plan assumed.** `App::update(ctx, frame)` is
   `App::ui(ui, frame)`; panels are shown inside a `&mut Ui`, not a `&Context`; `SidePanel` is
   `Panel::left`; `default_width` is `default_size`; `raw_scroll_delta` is
   `smooth_scroll_delta`. Read the vendored crate before writing an integration, not the docs
   for a different version.
2. **`wgpu` 30 rejects a depth bias on a line list.** The plan's "lines: depth test on, no
   depth write" was right, but the coplanar-over-the-surface problem it leaves cannot be fixed
   with `DepthBiasState` for lines. It is fixed by lifting the geometry instead — a real
   geometry change, visible in `scene::GRATICULE_LIFT`.
3. **The depth buffer's *ratio* matters, not its far value.** The stars were inside the frustum
   and still invisible. A near/far ratio of 10 000 puts most of the depth range in the first
   few kilometres, so a line at 90 % of the far plane loses the depth test. The camera now
   carries `near_ratio` and `far_ratio` explicitly, and the star radius is a fraction of the
   far plane rather than a multiple of anything else.
4. **The CPU projection in the window and the GPU pass are two different renderers.** The plan
   said the app "owns a `wgpu` render pass and an egui overlay". What shipped is an egui
   painter in the window plus a real `wgpu` pass in the offscreen verification path, sharing
   `SceneData`. That is honest and it works, but the window does not yet use the pipelines, and
   the changelog says so under "Not built yet".

The plan's verification rule was the one that mattered: every one of the five defects it
predicted the tests would miss *was* missed by the tests, and was found only by rendering and
looking.
